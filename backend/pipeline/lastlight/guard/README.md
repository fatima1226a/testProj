# Backend release-guard

Один набор предикатов используется CLI, management-командой `load_release`
и тестами реальных HTTP-ответов. Код ничего не исправляет и не присваивает
научным проверкам `passed`. Отчёт содержит номер правила, статус и причину;
ошибка правила даёт ненулевой код завершения.

Из корня проекта:

```sh
python3 -m pipeline.lastlight.guard packages/sim/fixtures/mini-2x200
```

| Правило | Что проверяется |
| --- | --- |
| A1 | Для final: несинтетические источники, URL/запрос, версия, время UTC, SHA-256 |
| A2 | Совпадение id и SHA-256 источников в fetch-manifest и provenance |
| A3 | `not_applicable`: формулировка находится в отсутствующем ТЗ фронтенда |
| A4 | У переданных записей истории правильный dataset_id/mode и отдельное DEMO DATA |
| B1 | У passed/failed есть время, измерение, допуск, существующий отчёт с верным хешем |
| B2 | Passed уровня 1/паритета подтверждены CI того же коммита и хеша фикстур |
| B3 | Passed уровней 2–4 подтверждены датированным протоколом с именем подписанта |
| B4 | У demo уровни 1–4 остаются pending |
| D1 | Одинаковый datasetId, SHA-256 точных байтов sites.json |
| D2 | Существующий datasetId не перезаписывается другим содержимым |
| D3 | Схемы и существующие программные проверки связей документов |
| C4 | Переданные сырые ответы API побайтно совпадают с тремя файлами выпуска |

A3 не считается пройденным. A4 проверяет доступное API представление; реальное
отображение в интерфейсе требует фронтенда. Без записей истории A4 получает
pending. Без ответов API C4 получает pending. Без контекста БД D2 имеет
not_applicable; при загрузке команда всегда проверяет его в транзакции,
включая повторную проверку результата get_or_create при конкурирующей загрузке.
Сравнение всех трёх документов — более строгая политика неизменности, чем
минимальное требование D2 только к хешу sites.json.

`ok=true` означает отсутствие нарушений в области backend, а не полную
готовность деплоя. `--require-complete` также возвращает код 1, если остались
pending правила backend (например, ещё не переданы API/история).
Научные pending и честные failed в validation.json сами по себе не блокируют
выпуск: запрещены неподтверждённые утверждения об успешных проверках.
Полноценный CI с обязательным branch protection и проверкой фронтенда пока
не настроен; наличие модуля само по себе не блокирует слияние или деплой.

## Форматы свидетельств

ТЗ описывает смысл этих отчётов, но не даёт точной JSON-формы. Ниже зафиксирован
исходный машинный контракт, который предстоит согласовать с генераторами CI
и ручных протоколов. Основные схемы sites/provenance/validation не менялись.

Выпуск с реальными источниками содержит `fetch-manifest.json`:

```json
{"sources": [{"id": "source-id", "sha256": "64 lowercase hex characters"}]}
```

Множество id/хешей должно точно совпадать с несинтетическими sources в provenance.
Сами исходные DEM не обязаны входить в каталог выпуска. A2 сравнивает записанные
хеши; он не скачивает и не пересчитывает недоступные исходные файлы.

Для passed уровня 1 или parity нужен `ci-report.json`:

```json
{
  "commit": "40 or 64 lowercase hex characters",
  "versions": {"python": "version", "typescript": "version"},
  "sitesSha256": "SHA-256 of exact sites.json bytes",
  "manifestSha256": "SHA-256 of exact fixture manifest bytes",
  "checks": {"level-1": {"status": "passed"}, "parity": {"status": "passed"}}
}
```

Соответствующие записи validation.json ссылаются на ci-report.json и его хеш.
Ожидаемый коммит передаётся независимо через `--commit` или GITHUB_SHA;
не берётся из самого отчёта. Манифест по умолчанию `manifest.json` внутри выпуска,
или путь из `--manifest`. Проверяется хеш манифеста, но не независимость подписей
H1 и не повторный запуск всех тестов — это задача CI. Если CI был подделан,
guard не может определить это по одним самосогласованным JSON-файлам.

Для passed уровня 2, 3 или 4 отчёт содержит:

```json
{
  "checkId": "level-2",
  "status": "passed",
  "signedBy": "Reviewer name",
  "signedAt": "2026-01-01T00:00:00Z",
  "sitesSha256": "SHA-256 of exact sites.json bytes"
}
```

Это фиксация имени и даты подписанта, не криптографическая проверка его личности.
Для всех выполненных проверок пути отчётов ограничены каталогом выпуска,
проверяются существование и SHA-256. Если JSON-отчёт объявляет sitesSha256,
он обязан совпадать с текущим набором. Подписанные реальные протоколы этим
кодом не создаются. Синтетические отчёты тестов живут только во временных папках.

## Проверка после загрузки

```sh
python3 -m pipeline.lastlight.guard path/to/release \
  --api-base-url http://localhost:8000/api/datasets/DATASET_ID/ \
  --history path/to/history-response-results.json --require-complete
```

`--history` принимает массив `results` из реального GET /api/runs/, а не весь
объект пагинации. Для этой проверки передаются записи именно данного выпуска.
JWT не передаётся в URL; guard сам не получает и не печатает токены. При необходимости
историю выгружают отдельно с авторизацией заголовком. Проверка реальных HTTP-ответов
также встроена в `server/tests/test_api.py` и требует настоящих DRF/JWT/CORS.

Тесты guard не требуют Django или сети:

```sh
python3 -m unittest pipeline.tests.test_guard -v
```
