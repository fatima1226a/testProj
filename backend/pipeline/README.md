# Демо-набор LAST LIGHT

Запуск из корня проекта, Python 3.11 или новее:

```sh
python3 -m pipeline.lastlight.demo
python3 -m pipeline.lastlight.demo --validate-only
python3 -m unittest discover -s pipeline/tests -v
```

Выход по умолчанию: `packages/sim/fixtures/mini-2x200/`. Параметры:
`--output PATH`, `--seed INTEGER` (по умолчанию 42).
Одинаковый seed даёт побайтно одинаковый `sites.json`; время реальной
проверки в `validation.json` и `schema-report.json` обновляется.

Все координаты, профили и эфемериды синтетические. Окно: 200 часов, 1200 интервалов по 10 минут с
2026-01-01T00:00:00Z. У каждой площадки 360 узлов горизонта для высоты 2 м.
A всегда освещена, Земля видна. У B гора 20° на 180°, холм 4° на 315°,
ежедневная тень на часах 6–10 UTC, три закрытые серии Земли и отдельное
равенство горизонту. Набор позволяет проверять успешные планы и отказы
по батарее и Земле после подключения расчётного пакета.

Проверка схем не означает проверку физики: уровни 1–4 остаются `pending`.
Только служебная проверка схем получает `passed`, реальное время выполнения
и ссылку на отчёт с SHA-256. Источники внешних данных не скачиваются.
Функции P1 недоступны; дополнительных профилей и клонов нет.

Проверка работает без сети: `schema_validation.py` проверяет используемые
ключевые слова схем и отвергает неподдерживаемые. Это ограниченный валидатор,
а не полная реализация JSON Schema Draft 2020-12. При наличии пакета
`jsonschema` автоматически выполняется также проверка стандартным валидатором
и проверка самих схем. Необязательная зависимость — `pipeline/requirements.txt`.
Дополнительно проверяются связи документов, хеши, заданная временная сетка,
одинаковые длины профилей и свидетельства выполненных проверок.

Уточнения контракта, которые нужно согласовать с фронтендом перед интеграцией:

- `datasetId` включён в `sites.json` согласно D1, хотя его нет в краткой записи
  `SitesFile` раздела 4.
- Долгота принята положительной к востоку, в диапазоне [-180, 180].
- Зафиксированы имена полей provenance/validation, для которых ТЗ даёт
  смысловое описание: `sitesSha256`, `coordinateConventions`, `checks`,
  `report: {path, sha256}` и другие поля в схемах.

Sites v2 фиксирует stepMinutes=10 для нового demo; старый v1 со stepH=1 поддержан. Это изменение пользователя, а не заявление о согласовании контракта всей командой.
Тесты не создают подписанных независимых ожиданий H1; манифест фикстур,
Научные проверки будут отдельным шагом. Python refsim реализован; backend release-guard
реализован в [lastlight/guard/](lastlight/guard/README.md).

## Эфемериды JPL Horizons

`lastlight/ephem.py` запрашивает Солнце (10) и Землю (399) для наблюдателя
`coord@301` на Луне. Параметры запроса: `QUANTITIES=4`, `APPARENT=AIRLESS`,
`TIME_TYPE=UT`, CSV с точностью времени до секунд. Азимут в градусах от севера
по часовой стрелке. Долгота на входе — восточная [-180,180], в запросе [0,360).
Высота в CLI — метры, в SITE_COORD — километры.

Документация:
[Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html),
[система координат и величины](https://ssd.jpl.nasa.gov/horizons/manual.html).

После установки `requests` из requirements, пример **для тестовой точки**:

```sh
python3 -m pipeline.lastlight.ephem \
  --lat=-89.5 --lon=0 --height-m=2 \
  --start=2026-01-01T00:00:00Z --count=888 \
  --cache=/private/tmp/last-light-horizons-cache \
  --output=/private/tmp/last-light-ephem.json
```

`--height-m` задаётся явно: это полная высота наблюдателя над опорным эллипсоидом
Horizons, а не просто высота мачты над местным рельефом. Для реальной площадки
нужны согласованная система высот DEM и проверка преобразования в лунный
Mean-Earth frame Horizons. Пример 2 м не является решением для реальной точки.

По умолчанию шаг 60 минут, count=888. STOP_TIME включён: он равен
start+(count−1)×step. Допускаются count от 2 до 10000 и шаги 60/10 минут.
`--step-minutes=10` создаёт отдельный ряд для будущей проверки устойчивости,
который требует соответствующих stepMinutes/count в sites.json v2. Почасовой v1 остаётся отдельным форматом. Модуль выдаёт промежуточный
JSON `{hours, stepMinutes, sources}`, а не готовый выпуск sites.json.

Кэш содержит сырые ответы и метаданные: URL, полный запрос, версию API,
реальное UTC-время получения и SHA-256. Повторный запуск читает кэш без сети.
`--offline` запрещает загрузку при промахе. Нарушение хеша или неполная запись
останавливают работу; ошибочный ответ не кэшируется. Пропуски, n.a., неверные
углы, даты и количество строк отвергаются, значения не подменяются.

Прямой тестовый запрос из окружения 26.10.2026 остановился на DNS
(`nodename nor servname provided`). `requests` также пока не установлен;
доступ к PyPI/npm недоступен. Автотесты используют синтетические ответы
формата API и транспорт-заглушку, без сети. Реальный ответ JPL, координаты
двух рабочих площадок и три ручные сверки в веб-интерфейсе ещё не проверены.
Поэтому Блок 2 целиком пока не закрыт; статусы validation.json не изменялись.

P0 и P1 расчётного пакета реализованы в `packages/sim/src/`. Отдельная Python-
реализация `lastlight/refsim.py` поддерживает simulate, minCapacityFor и uncertainty;
дифференциальный прогон включён в `npm test` пакета sim. Независимые ожидания
с подписями H1 остаются отдельным этапом.

## Рельеф и горизонт

`terrain.py` читает одноканальные DEM через rasterio/pyproj. CRS, размер пикселя,
маска nodata, масштаб и сдвиг берутся из GeoTIFF. Система отсчёта высот и
лунная система координат должны быть явно записаны в тегах HEIGHT_DATUM,
BODY_FRAME или переданы из PDS label с указанием metadata_source. Неизвестные
единицы высоты, отсутствие CRS, несовместимые системы near/far и пропуски
останавливают расчёт. Высоты приводятся к метрам; километры также поддержаны
при явно указанной единице. Используются только сферические лунные CRS;
между разными body frame/датумами автоматического преобразования нет.

`horizon.py` строит лучи по большим кругам от местного севера по часовой
стрелке. По каждому азимуту берётся максимум по обоим DEM:
`degrees(atan((terrainHeight - groundHeight - mastM)/d) - d/(2R))`.
Точка d=0 исключена, отрицательный горизонт сохраняется. Радиус R берётся из
CRS DEM, а не подставляется из памяти. По умолчанию мачта 2 м, N=360; N=720
также поддерживается без дублирования последнего азимута.

Near DEM требуется 5 м/пиксель, far — 240 м/пиксель. Near сканируется в радиусе
8 км (вписанная окружность центрированного квадрата 16×16 км, без углов квадрата),
с шагом 5 м; far сканируется с шагом 240 м, включая перекрытие с near.
Наличие покрытия проверяется на каждой выбранной точке. В перекрытии отчёт
показывает среднее смещение, максимальное расхождение и RMSE высот.

Пример после установки геозависимостей из requirements:

```sh
python3 -m pipeline.lastlight.horizon \
  --near path/to/near.tif --far path/to/far.tif \
  --metadata path/to/metadata.json \
  --lat=-89.5 --lon=0 --far-radius-m=100000 \
  --azimuth-count=360 --output=/private/tmp/last-light-horizon.json
```

metadata.json имеет форму `{ "near": { "vertical_unit": "m", "height_datum":
"из label", "body_frame": "из label", "metadata_source": "путь/ссылка label" },
"far": { ... } }`. Это описание формы; конкретные значения из продуктов ещё
предстоит выбрать. Если все сведения есть в тегах GeoTIFF, metadata не нужен.

Результат содержит `horizon` и отчёт стадии. `report.status=passed` означает
успешное чтение выбранных лучей, а не научную проверку уровней 1–4. Расчёт не
правит demo-набор и его validation.json. Дальности, дискретизация лучей,
выборка ближайшего пикселя и исключённые углы near требуют проверки сходимости
на реальных продуктах. Дальность far обязательно задаётся в CLI; значение
100 км в примере не является доказанной достаточной дальностью.

Проверки искусственной горы, дальней горы, кривизны, отрицательного горизонта,
направлений у полюса, мачты и перекрытия работают без геобиблиотек. Тесты
реального адаптера GeoTIFF находятся в test_terrain_raster.py и явно пропускаются,
если numpy/rasterio/pyproj не установлены. В текущем окружении эти зависимости
не удалось установить; реальные LOLA/PGDA файлы пока не обработаны.


## Обновление mini-2x200

Текущий генератор выпускает v2 с window.stepMinutes=10 и count=1200,
Site.stepMinutes=10 на обеих площадках. Временные метки проверяются на шаг
ровно 600 секунд, без интерполяции ранее загруженных эфемерид: набор синтетический.
Имя мини-набора обозначает две площадки и 200 часов, а не число строк v2.
Новый datasetId включает v2-10min, поэтому не перезаписывает старый выпуск по D2.
Генератор обновляет sites SHA-256, ссылки на отчёт схем и все три документа.

В provenance добавлена secondSignature с привязкой к SHA-256 sites.json.
Поле заполняется честным pending/null до реального независимого подписания.
Проверка связей запрещает несовместимый шаг площадки/окна и неполную подпись
со статусом signed. Дополнительные произвольные поля provenance по-прежнему
запрещены; расширение имеет явную структуру в JSON-схеме.
