# Django API LAST LIGHT

Доступны два явно выбираемых режима: `LAST_LIGHT_API_BACKEND=django` (по умолчанию,
стандартные Django-вьюхи и сессии без сторонних библиотек) и `drf` (DRF,
SimpleJWT и django-cors-headers). Режим drf требует установки зависимостей
и не переключается молча на сессии при ошибке установки. База — SQLite.
`accounts` содержит пользователя и регистрацию, `datasets` — неизменяемые
выпуски, `runs` — личные снимки расчётов. `mission` выполняет отдельную
демонстрационную симуляцию условий посадки и энергоснабжения.

## Локальный запуск

На macOS откройте `server/start.command` двойным кликом. Он выбирает Python
из `server/.venv`, запускает сервер и открывает браузер после ответа API.
Из терминала в папке server: `./start.command` (другой порт: `--port 8001`).
Проверка без открытия браузера и TCP-порта: `./start.command --check`.
На Windows запускайте `server\start.bat` (те же аргументы, например `--port 8001`).

Для подготовки окружения из папки server: `python3 setup_local.py`.
Создаётся `server/.venv` (на Windows — `server\.venv-win`: в синхронизируемой папке
одно окружение не может обслуживать обе ОС). Неработающее окружение (перенесённое,
с удалённым базовым Python) пересоздаётся. Уже установленный системный Django используется без
повторной загрузки. Если Django отсутствует, установщик скачивает его из PyPI.
Полная установка: `python3 setup_local.py --full` — зависимости DRF/JWT и
официальные файлы Swagger UI сохраняются локально. Для полной установки нужен
доступ к PyPI и unpkg.com. После неё Swagger UI работает без CDN.

Если Django уже установлен, из корня проекта:

```sh
python3 server/run_local.py
```

Это локальный запуск на 127.0.0.1:8000 с DEBUG, миграциями и загрузкой demo.
Swagger: http://127.0.0.1:8000/swagger/ (также `/api/docs/`).
Схема OpenAPI: `/api/schema/`. Документация доступна без входа в обоих режимах API.
В режиме django выполните login прямо в Swagger; CSRF-заголовок добавляется автоматически.
В режиме drf получите access token и укажите его через Authorize.
Полный Swagger UI загружается с unpkg.com. Если CDN недоступен, остаётся локальный
интерфейс со списком методов и выполнением запросов, без внешних зависимостей.
Корневой адрес http://127.0.0.1:8000/ перенаправляет на документацию.
`run_local.py` проверяет наличие Django и при пустой/перенесённой `.venv` использует
базовый Python, если Django установлен в нём; выбранный путь выводится в терминале.
Проверка без запуска TCP-сервера: `python3 server/run_local.py --check` из корня
проекта или `python3 run_local.py --check` из каталога server.
Другой порт: `--port 8001`. Постоянный секрет хранится в `server/.env`:
он автоматически читается при локальном запуске, через manage.py, WSGI и ASGI.
Переменные окружения имеют приоритет над `.env`.
run_local.py предназначен только для разработки.

При настройке новой копии проекта создайте `.env` один раз из корня проекта:

```sh
python3 - <<'PY'
import os
import secrets
fd = os.open("server/.env", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as stream:
    stream.write("LAST_LIGHT_SECRET_KEY=" + secrets.token_urlsafe(48) + "\n")
PY
```

Команда не перезаписывает существующий файл. `.env` исключён из Git;
`.env.example` содержит только пример без секрета. Формат: `KEY=value`,
значения можно заключать в кавычки; комментарии — на отдельных строках.
Подстановка shell-переменных не выполняется. Не публикуйте `.env`.

В среде агента открытие порта запрещено (`Operation not permitted`), поэтому
работающий TCP-сервер здесь не подтверждён. Проверки Django, миграции, загрузка
demo и тесты HTTP-вьюх через Django Client выполнены. Команда выше предназначена
также для запуска в обычном терминале с разрешённым доступом к localhost.

Для режима DRF/JWT, в отдельном окружении Python:

```sh
python3 -m pip install -r server/requirements.txt
export LAST_LIGHT_API_BACKEND=drf
export LAST_LIGHT_DEBUG=1
export LAST_LIGHT_FRONTEND_ORIGINS=http://localhost:5173
python3 server/manage.py migrate
python3 server/manage.py load_release packages/sim/fixtures/mini-2x200
python3 server/manage.py runserver
```

Для постоянного сервера задайте собственный секрет через настройки окружения
хостинга или закрытый `.env` и сохраняйте его между перезапусками.
В репозиторий секрет не помещается.
Дополнительные переменные: `LAST_LIGHT_ALLOWED_HOSTS`, `LAST_LIGHT_DB_PATH`.
Если проект лежит в синхронизируемой папке (OneDrive, iCloud), укажите `LAST_LIGHT_DB_PATH`
вне неё: синхронизация SQLite-файла приводит к блокировкам и может повредить базу.
Домены CORS перечисляются через запятую; `*` не используется.

Маршруты:

| Метод | Путь | Доступ |
| --- | --- | --- |
| POST | `/api/auth/register/` | Без входа; username, email, password |
| GET | `/api/auth/csrf/` | Режим django: CSRF token и cookie |
| POST | `/api/auth/login/` | Режим django: вход, cookie сессии и новый CSRF token |
| POST | `/api/auth/logout/` | Режим django: выход из сессии |
| POST | `/api/auth/token/` | Режим drf: username/password → access/refresh |
| POST | `/api/auth/token/refresh/` | Режим drf: refresh → access |
| GET | `/api/datasets/` | Без входа; список выпусков |
| GET | `/api/datasets/<datasetId>/sites/` | Без входа; исходные байты JSON |
| GET | `/api/datasets/<datasetId>/provenance/` | Без входа |
| GET | `/api/datasets/<datasetId>/validation/` | Без входа |
| GET, POST | `/api/runs/` | Авторизация выбранного режима, только свои записи |
| GET, PATCH, DELETE | `/api/runs/<id>/` | Авторизация; PATCH только label |

В режиме django JWT-маршруты возвращают 501 и не выдают поддельные токены.
Нужно сначала GET /api/auth/csrf/, затем POST /api/auth/login/ с JSON username/password,
cookie и заголовком X-CSRFToken. Вход обновляет CSRF token; использовать новый
токен из ответа для последующих POST/PATCH/DELETE, включая logout.
Регистрация также требует CSRF. SameSite=Lax остаётся стандартным; локальный
фронт на localhost:5173 использует `credentials: "include"`. Для разных сайтов
нужна отдельная конфигурация cookie/хостинга. Разрешённые CORS-источники также
являются CSRF_TRUSTED_ORIGINS; посторонние origins запрещены. CSRF не отключается.

В режиме drf JWT передаётся только заголовком `Authorization: Bearer …`. Входящие plan/result
проверяются на JSON-объекты, конечность чисел и отсутствие ключей авторизации
или значений, похожих на JWT. Результат хранится как снимок, не как подтверждённый
сервером научный расчёт. Регистрация не выдаёт токен автоматически.

POST runs принимает `dataset_id`, `site_id`, `plan`, `result`, необязательный
`label`. Сервер определяет `dataset_mode` сам, для demo возвращает отдельное
поле `dataset_notice: "DEMO DATA"`, которое не зависит от редактируемого label.
Максимум 50 записей на пользователя;
старые удаляются. Роль staff/superuser не открывает чужие записи через API.
Админка доступна по http://127.0.0.1:8000/admin/ и позволяет управлять пользователями.
Для первого входа создайте суперпользователя из каталога server:
`python3 manage.py createsuperuser`. Пароль вводится в терминале и не отображается.
Корневой адрес сервера перенаправляет на Swagger. История расчётов в админке не подключена.
Автосохранение после расчёта выполняет
будущий фронтенд вызовом POST.

`load_release` вызывает общий [backend release-guard](../pipeline/lastlight/guard/README.md),
затем транзакционно сохраняет проверенный снимок байтов трёх документов.
Повторная загрузка идентичного выпуска идемпотентна;
изменённый выпуск с тем же datasetId отвергается. Ограничения неизменности
реализованы в сервисах и Model.save; прямые SQL и QuerySet.update обходят их.
При нарушении команда завершается ошибкой с номером правила, без записи выпуска.
Для passed уровня 1/паритета нужны `--commit SHA` (или GITHUB_SHA), ci-report.json
и хеш манифеста фикстур; внешний манифест задаётся через `--manifest PATH`.
Guard не запускает симуляцию и не создаёт научных отчётов. A3 относится к фронту;
проверки A4/C4 по реальным HTTP-ответам входят в тесты API. Деплой и branch protection
пока не настроены.

Восстановление пароля по email, SMTP, PostgreSQL и деплой — последующие этапы.
Исходные JSON-схемы не менялись. Пути datasets являются предложением API,
поскольку ТЗ не фиксирует их. Для истории принят формат snake_case.

## Аналитика миссии

Публичный `POST /api/mission/` принимает `Content-Type: application/json`:

```json
{"latitude": -85.0, "longitude": 30.0, "timestamp": "2026-06-01T12:00:00Z"}
```

Широта должна находиться в диапазоне [-90, -60], долгота — [-180, 180],
время — в ISO 8601 с часовым поясом. Некорректный ввод возвращает HTTP 400.
Корректный расчёт возвращает HTTP 200, включая прогноз с вердиктом `FAIL`.

Основные блоки ответа для фронтенда:

- `status`, `failure_reasons`: `SUCCESS` или `FAIL` и коды причин.
- `forecast.timeline`: 24 последовательных часовых интервала `[start, end)` в UTC.
  `generation_w`, `consumption_w` — мощности в ваттах; `generated_energy_wh`,
  `consumed_energy_wh` — энергия за интервал. Температура и освещение берутся
  на начало часа, `battery_soc_start_percent` — начальный заряд,
  `battery_soc_percent` и `energy_wh` — заряд и энергия в конце часа.
  Начальное состояние батареи и единицы измерения также есть в `forecast`.
- `landing_zone`: сетка с шагом 25 м внутри круга 100 м и 32 точки его границы,
  всего 77 точек. `samples` содержит координаты, высоты, уклоны и признак
  безопасности каждой точки. `safe_radius_estimate_m` — наибольший проверенный
  радиус с шагом 25 м без небезопасных отсчётов внутри. Склоны выше 15° и точки
  вне разрешённой полосы широт считаются небезопасными. Доступны максимум,
  среднее, разброс и стандартное отклонение уклона.
- `power`, `dte`: энергетические итоги, заряд батареи и интервалы связи.
- `dust`: накопление пыли от момента посадки, начальная/конечная эффективность
  панелей и потери генерации в Wh. Каждый запрос начинает новую миссию с чистыми
  панелями. Демонстрационная формула эффективности: `0.6 + 0.4 * exp(-0.002 * hours)`.
  В почасовой генерации используется средняя эффективность за интервал;
  `clean_generation_w` и `dust_loss_w` позволяют сравнить чистые и запылённые панели.
- `radiation`: безразмерный сценарный индекс 0–100 и уровень LOW/MODERATE/HIGH,
  начальное значение, максимум и среднее за сутки. `forecast.timeline[].radiation`
  содержит почасовые значения. Индекс использует высоту Солнца и искусственный
  периодический сценарий активности. Фон сохраняется в тени. Это не измерение
  дозы и не прогноз вспышек: `observed_space_weather=false`, `flare_probability=null`.
  Радиационный индекс пока носит информационный характер и не меняет вердикт.
- `thermal_shock`: оценка термического риска по соседним температурным отсчётам,
  максимум напряжения, число переходов свет/тень и интервалов высокого риска.
  `reference_stress_test` отдельно проверяет переход от -200 до +120 °C за час
  (перепад 320 °C). Для демонстрационного материала приняты E=70 GPa,
  коэффициент расширения 23e-6/K и допустимое напряжение 150 MPa.
  Модель полностью ограниченного одномерного расширения использует модуль
  упругой оценки `stress = E * alpha * abs(delta_temperature)`; эталонный тест
  даёт 515.2 MPa и HIGH. LOW означает долю допустимого напряжения <0.5,
  MODERATE — от 0.5 до 1, HIGH — от 1. Первый отсчёт не предполагает неизвестную
  предысторию и имеет нулевой перепад. Почасовые значения находятся в
  `forecast.timeline[].thermal_shock`. Оценка не моделирует температурные
  градиенты внутри детали, пластичность, трещины или усталость; показатели
  термошока носят информационный характер и не меняют вердикт миссии.
- `signal_latency`: время распространения сигнала в вакууме: `one_way_s`
  в одну сторону, `round_trip_s` туда-обратно. В демонстрационной модели
  расстояние между центрами Земли и Луны меняется от 363300 до 405500 км
  с выбранным периодом 28 суток; эпоха/фаза не являются реальной эфемеридой.
  Задержка равна `distance_km / 299792.458`, примерно 1.21–1.35 с в одну сторону.
  Эти значения также есть в каждом часовом отсчёте. `link_available` совпадает
  с DTE: при отсутствии видимости `dte_one_way_s` и `dte_round_trip_s` равны
  null, тогда как геометрическое время остаётся определено. Задержки обработки,
  ретрансляции и геометрия конкретной наземной станции не учитываются.
- `safe_haven`: при `FAIL` автоматически проверяются кандидаты в круге 1 км
  по сетке 100 м, от ближайших к дальним (максимум 316 кандидатов). Каждый проходит
  полный прогноз на те же сутки с пылью, проверкой батареи и 100-метровой зоны.
  `FOUND` возвращает в `destination` координаты ближайшего успешного кандидата,
  расстояние, направление и ключевые итоги его проверки; `NOT_FOUND` означает,
  что подходящий кандидат не найден; `NOT_NEEDED` — исходная точка успешна.
  Исходный `FAIL` сохраняется. Ближайший кандидат выбирается среди точек сетки;
  проходимость пути между точками не проверяется (`route_validated=false`).
- `summary`: часы света и тени, самый длинный интервал тени и отсутствия связи,
  температурные экстремумы и оценка зоны посадки.
- `assumptions`, `metadata`: параметры аппарата, версия формата и допущения.

Небезопасная зона даёт `UNSAFE_LANDING_ZONE` и влияет на общий вердикт.
Батарея проверяется по минимуму за весь прогноз, включая начальный заряд.
Рельеф, освещение и положение Земли синтетические. Оценка радиуса относится
к проверенным точкам и не гарантирует отсутствие препятствий между ними.

## Проверки

Проверка выбранного режима (по умолчанию django, установка DRF не нужна):

```sh
python3 server/manage.py check --settings=server.config.test_settings
python3 server/manage.py test server.tests server.mission --settings=server.config.test_settings
```

Для полной проверки обоих режимов без пропусков установите зависимости в
окружение проекта и выполните оба запуска из корня проекта:

```sh
server/.venv/bin/python -m pip install -r server/requirements.txt
LAST_LIGHT_API_BACKEND=django server/.venv/bin/python server/manage.py test server --settings=server.config.test_settings --exclude-tag=drf
LAST_LIGHT_API_BACKEND=drf server/.venv/bin/python server/manage.py test server --settings=server.config.test_settings --exclude-tag=django
```

Метки исключают тесты другого режима только в соответствующем запуске:
JWT/CORS проверяются в drf, сессии/CSRF — в django, общие тесты выполняются
в обоих. Тест отсутствующих зависимостей имитирует их отсутствие в отдельном
интерпретаторе и выполняется даже после полной установки пакетов.

Отдельные тесты реальных Django-моделей и миграций без DRF/JWT/CORS:

```sh
python3 server/manage.py test server.tests.test_models --settings=server.config.model_test_settings
python3 server/manage.py makemigrations --check --dry-run --settings=server.config.model_test_settings
```

Оба тестовых settings используют SQLite в памяти; слабый быстрый хешер
используется исключительно в тестах. Эти настройки нельзя применять к серверу.

В окружении Windows (`.venv-win`, Python 3.11) установлены Django 5.2 и зависимости
server/requirements.txt. Прошли 67 тестов в режиме django, 60 тестов в режиме drf
(`LAST_LIGHT_API_BACKEND=drf`, тесты другого режима пропускаются) и 13 тестов моделей. Тесты регистрации, входа/выхода, прав, CSRF,
CORS, лимита истории и guard A4/C4 выполняются через настоящие Django-вьюхи
и middleware. Проверки CSRF включают Client(enforce_csrf_checks=True).
Тесты DRF/JWT пропускаются в режиме django; чтобы выполнить их, нужно
установить server/requirements.txt и задать LAST_LIGHT_API_BACKEND=drf.
